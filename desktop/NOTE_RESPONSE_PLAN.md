# 笔记响应类型整理计划

目标：将 feed 响应整理为便于业务使用的 Go 类型，完整保留媒体选项，默认最佳质量候选排第一。只做数据解析与整理，不引入下载、播放、额外请求或 UI。

## 样本确认

依据 `internal/xhsapi/testdata/note_response.json`（用户提供样本的唯一保留副本），顶层为 3 个 `note_card` 包装项的数组，真实接口对应 `data.items`：

- 视频：EF4 有 1 路 720×1280，EF5 有 4 路（720×1280、1080×1920、1440×2560、2160×3840）；均为 MP4 / 60 FPS，各有主 URL 和 1 个备用 URL。所有流的 `quality_type` 都为 HD，不能仅按此字段判断清晰度。
- LivePhoto：笔记类型为 `normal`，包含 8 张图片；每张 `live_photo=true`，动态流位于图片自身的 `stream.EF4`。样本未提供动态流的宽高、时长、FPS，不能用静态图片尺寸代填。
- 普通图文：1 张图片，`live_photo=false`，`stream` 为空。
- 图片均提供 `WB_PRV`、`WB_DFT` 场景；`url_pre` / `url_default` 也要保留。样本的 `url` 为空。
- 视频同时提供 `media` 和对象形式的 `media_v2`；此前响应中 `media_v2` 也出现过 JSON 字符串形式。

以上数量和规格仅描述当前样本，不作为解析上限或固定结构。编码分组、每组流数、备用 URL 数、图片数、图片场景数及同场景候选数均按响应动态读取。

## 类型与入口

在 `internal/xhsapi` 中新增独立的笔记类型、解析和整理文件；原始结构使用内部 DTO，业务层得到统一的结果类型：

| 类型 | 内容 |
| --- | --- |
| `Note` | ID、原始笔记类型、标题、正文、作者、互动、话题、时间、位置、图片、可选视频、HasLivePhoto、Raw |
| `NoteVideoInfo` | 视频 ID、业务 ID、时长、原始尺寸、MD5、HDR/DRM、封面信息、完整 Streams、来源元数据 |
| `VideoStream` | 编码分组和原始编码值、规范编码名、封装、分辨率、FPS、码率、时长、大小、音频、HDR、质量指标、主/备用 URL、来源与原始序号 |
| `NoteImageInfo` | 图片原始序号、FileID、宽高、全部 Variants、LivePhoto 标志、完整 MotionStreams |
| `ImageVariant` | 唯一完整 URL、优先 Scene/来源、全部 Sources、原始序号；有响应依据时才填格式/尺寸 |

内部按 JSON 对象的动态分组名和记录切片解析，同时保留分组的响应顺序；整理后的 Streams/MotionStreams 使用动态切片，不定义固定的 EF4/EF5/EF6/EF7 字段或固定长度数组。图片 Variants 使用切片，同一个 Scene 可以对应多个候选，不能用 `map[Scene]URL` 覆盖记录。原始分组名、空分组和来源数据也保留，可通过纯方法按编码/Scene 筛选。

入口拟为 `Response.DecodeNotes() ([]Note, error)`，读取 `Data.items`；`ParseNoteItems(raw) ([]Note, error)` 读取样本项数组，两者共用解析与整理逻辑。`GetNote` 保持返回原始 Response。避免与现有搜索枚举 `NoteVideo` / `NoteImage` 重名。

## 解析与整理规则

1. **视频全量抽取**：遍历全部编码分组及每组的全部流，不设白名单、每组条数或总条数上限。EF4 可以有多路，EF6/EF7 和未来新分组同样完整解析；未知编码仍能读取 URL、尺寸、码率等通用字段。EF4/EF5 可依据现有 Python 映射为 H.264/H.265，同时保留原值，其他编码不猜测。保留同编码不同分辨率、同分辨率不同码率及同规格不同地址的所有流。
2. **双来源兼容**：`media_v2` 支持对象、JSON 字符串、null/缺失；与 `media` 做保守合并。同一来源内部不合并记录；跨来源仅对确认相同的流做一对一匹配，不能多条压成一条。匹配需主 URL、编码分组及双方已提供的流类型、封装、尺寸、FPS、码率等核心字段一致；缺乏身份依据或存在冲突时分别保留。匹配后的备用 URL 稳定取并集，缺失字段互补；各来源的完整记录通过 Sources 保留。某个来源解析失败时返回可用结果与带字段路径的错误，便于调用方处理。
3. **URL 与元数据**：保留每条流的 master_url、不同的兼容 url 和全部不同 backup_urls；去除主/备之间的重复和空地址，不改写签名参数、不探测链接。可提供主 URL → url → 备用 URL 的候选列表。原始重复值通过内存中的 Sources.Raw 及单独保存的原文追溯，Pretty JSON 不重复嵌入 Raw。保留视频/音频码率、声道、旋转、HDR、default_stream、stream_desc、weight、VMAF/PSNR/SSIM/SR 等信息；opaque1、bound/bbox 等扩展通过原始元数据保留。
4. **图片与 LivePhoto**：任意数量的图片保持笔记顺序；逐张遍历整个 info_list 及 url_default/url_pre/url，按完整非空 URL 去重，优先选 WB_DFT（兼容 WebDft/WEB_DFT）记录作为代表，缺失字段从同 URL 来源补充，冲突及全部 Scene/来源通过 Sources 保留。Scene 使用开放字符串，同 Scene 的不同地址、未知/缺失 Scene 的地址均保留；空地址留在原始记录中。静态图与动态流归属同一张图片，动态流复用同样的全分组/全流解析；支持 LivePhoto 多编码、多清晰度、多备用地址、静态图与 LivePhoto 混排，以及标记为 LivePhoto 但未返回动态流的情况。
5. **类型兼容**：数字/字符串 ID 无损转字符串，避免 video_id 经 float64 丢精度；计数兼容数字、数字字符串、空串。时间使用明确单位：笔记时间戳为毫秒、视频 metadata/capa 时长为秒、流时长为毫秒。可选值区分缺失与 0，未知字段通过 Raw 保留。

## 默认排序：全部保留，最佳候选在前

- **视频流**：有播放 URL 的流在前；按像素数降序、FPS 降序。同规格按固定编码顺序分组，同编码内按视频码率降序（缺失时参考平均码率），最后按来源原始顺序稳定排列。跨编码不直接用码率判定画质，未知规格不补造；编码顺序仅用于同规格稳定排序。
- **图片候选**：WB_DFT（WebDft）在前，随后其他 DFT、url_default、其他场景、url、PRV/url_pre；同优先级存在尺寸依据时按像素数降序，其余保持来源顺序。同 URL 只返回一个候选，其他 Scene/来源收在 Sources，按 Scene 查询会包含合并来源。
- **来源顺序可追溯**：仅排序媒体候选，不改变笔记或图片顺序。质量排序独立为纯函数，业务可重新筛选/排序；不会只返回首项，也不将服务器 default_stream 等同于最高画质。
- 本样本视频第一候选应为 EF5 / 2160×3840 / 60 FPS，其余候选全部保留。其他响应按实际完整列表排序，不能硬编码首选编码、分辨率或候选数量。该顺序依据响应元数据，实际画质及播放兼容性由业务自行判断。
